# Dataset Column Inventory

This document inventories the columns used in the Beta journal-entry dataset, separating source/accounting fields from generated metadata and reference-only answer-key fields.

The dataset is **posting-line-level**: each row represents an accounting line, while multiple rows can share a `posting_id` and belong to the same journal entry. Metadata described as entry-level is propagated across all posting lines in that journal entry.

## 1. Source and structural fields

These fields come from the prepared raw dataset or support row-level traceability. They are not generated forensic metadata.

| Column | Description | Notes |
|---|---|---|
| `source_row_id` | Unique identifier for an original posting line | Preserves alignment with the source dataset and answer key. |
| `posting_id` | Identifier shared by all lines in a journal entry | Used to group posting lines into journal entries. |
| `document_date` | Date associated with the accounting document | Source date field. |
| `posting_date` | Date the transaction was posted in the accounting system | Distinct from document and entry dates. |
| `entered_date` | Date and time the transaction was entered | Used for weekend and after-hours analysis. |
| `gl_account` | General-ledger account identifier | Source account code. |
| `gl_account_name` | General-ledger account description | Used by cash-account identification. |
| `amount` | Monetary amount of the posting line | Source amounts are denominated in euros (EUR). |
| `cd_flag` | Debit/credit indicator | Expected values are `D` or `C`. |
| `user` | User associated with entering the transaction | Source user identifier/name. |
| `tax_rate` | Tax rate associated with the posting line | Source numeric field. |
| `ref_id` | Reference identifier associated with the posting | Retained from the source data. |
| `text` | Transaction description or text field | Retained from the source data. |

## 2. Generated metadata fields

These fields are generated by the metadata pipeline. They describe characteristics of posting lines or journal entries; they do not, by themselves, establish that a transaction is fraudulent.

| Column | Purpose / definition | Granularity | Validation status |
|---|---|---|---|
| `involves_cash` | Indicates whether the journal entry involves a cash account, based on cash identification in account names. | Entry-level; propagated to all lines in the entry. | Custom-generated. |
| `high_cash` | Identifies cash activity exceeding the configured materiality threshold (default threshold: €1,500). | Confirm exact line-versus-entry propagation in the implementation documentation. | 100% agreement with the reference `high_cash` field across 256,232 rows. |
| `weekend_activity` | Indicates whether the journal entry was entered on a Saturday or Sunday. | Entry-level; propagated to all lines in the entry. | Custom-generated; used to reproduce the reference `weekend` classification. |
| `after_hours` | Indicates whether the entry time falls outside the configured business-hour window. Current reference-matching window: before 08:00 or at/after 18:00. | Entry-level; propagated to all lines in the entry. | 100% agreement with the reference `nwh` field across 256,232 rows. |
| `posting_delay_days` | Measures elapsed time in days between `document_date` and `entered_date`. | Posting-line-level. | Custom-generated; numerical measure, not itself a timely/late classification. |
| `promptly` | Categorizes posting timeliness using the calculated posting delay. The generated values reproduce the reference categories 1, 2, and 3. | Posting-line-level. | 100% agreement with the reference `promptly` field across 256,232 rows. |
| `round_10` | Indicates whether the absolute posting amount is a nonzero multiple of 10. | Posting-line-level. | Custom-generated; no reference comparison established. |
| `round_100` | Indicates whether the absolute posting amount is a nonzero multiple of 100. | Posting-line-level. | Custom-generated; no reference comparison established. |
| `round_1000` | Indicates whether the absolute posting amount is a nonzero multiple of 1,000. | Posting-line-level. | Custom-generated; currently produces zero detections in the full dataset. |

### Metadata interpretation notes

- **Entry-level versus posting-line-level:** Entry-level characteristics are assigned consistently to every posting line sharing the same `posting_id`. Posting-line-level fields are calculated separately for each row.
- **Reference agreement:** The four reconciled fields achieved 100% agreement with their corresponding answer-key fields: `weekend_activity` against `weekend`, `after_hours` against `nwh`, `promptly` against `promptly`, and `high_cash` against `high_cash`.
- **Agreement is not independent validation:** Reproducing the reference labels demonstrates consistency with the research dataset's definitions; it does not prove that those definitions are universally appropriate audit criteria.
- **Thresholds and configuration:** The high-cash threshold is configurable. The after-hours window is currently set to 08:00–18:00. Confirm the implementation and methodology before changing either.
- **Currency:** The source dataset uses EUR. Currency normalization is outside the current Beta scope.

## 3. Reference-only answer-key fields

The following columns exist in the research answer key but are not currently generated as part of the project's metadata pipeline.

| Column | Description | Current project treatment |
|---|---|---|
| `label` | Reference anomaly/fraud label. | Retained for reference and future evaluation; not generated by the metadata pipeline. |
| `marking` | Reference anomaly scenario or marking identifier. | Retained for reference; not currently reproduced. |
| `top_n` | Reference audit-scope indicator. | Retained for reference; not currently reproduced. |

The answer key also contains reference classifications used for reconciliation:

| Reference column | Corresponding generated field |
|---|---|
| `weekend` | `weekend_activity` |
| `nwh` | `after_hours` |
| `promptly` | `promptly` |
| `high_cash` | `high_cash` |

These answer-key fields are comparison targets, not additional generated metadata columns.

## 4. Dataset column summary

| Category | Columns | Count |
|---|---|---:|
| Source and structural fields | `source_row_id`, `posting_id`, `document_date`, `posting_date`, `entered_date`, `gl_account`, `gl_account_name`, `amount`, `cd_flag`, `user`, `tax_rate`, `ref_id`, `text` | 13 |
| Generated metadata | `involves_cash`, `high_cash`, `weekend_activity`, `after_hours`, `posting_delay_days`, `promptly`, `round_10`, `round_100`, `round_1000` | 9 |
| Reference-only answer-key fields | `label`, `marking`, `top_n` | 3 |

The generated metadata dataset therefore contains **22 columns** when the 13 source/structural fields and 9 generated metadata fields are combined. Reference-only answer-key fields are maintained separately.
